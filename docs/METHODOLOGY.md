# 实现与实验方法

## 从要求到实现

这项作业的重点不是重新训练 Jev，而是说明你如何查阅接口、创建可靠的标签、实现可替换的输入输出格式，并诚实评估。

先从官方接口确认状态、问题和响应字段；再选小而可审计的任务。公开分类标签来自 BANKING77，布尔和量表任务使用明确文字规则。代码把服务、模型适配器、数据与评测分开，使测试可以使用固定响应检查协议，而正式服务始终调用真正的模型。

请求经过四步：验证类型及大小 → 为每题生成 JSON Schema → 调用 OpenAI Responses → 校验概率与答案并返回。若模型拒答、截断、遗漏问题或给出无效概率，返回明确错误，不用随意默认答案掩盖失败。

## 公平性与指标

两个服务收到完全相同的 state 和 questions，只改变服务地址及 model 参数。评测器独立持有 expected，显式构建请求，阻止标签泄漏。请求按数据原顺序执行，两服务的先后顺序逐条交替。

报告按三个任务拆分，不合并不同任务的准确率：

- 分类：准确率、宏 F1、平衡准确率、混淆矩阵，以及多类 Brier（对所有类别平方误差求和）。
- 布尔：阈值预先固定为 0.5，报告同类指标和二元 Brier。
- 量表：以期望等级为标准，报告小数原值的平均绝对误差 MAE，以及就近等级准确率。

宏 F1 对各类别的 F1 取平均。失败请求在 accuracy_all 中是错误，在对应真实类别的 F1 中计为漏判。Brier/MAE 只对有效回答计算，所以还必须看 coverage（有效答案数/总答案数）。完全没有有效回答时这些指标为 null，不填写虚假的 0。

保存 HTTP 往返耗时（包含重试、排队、网络与生成），按任务报告 p50/p95。一个多题请求共用同一个耗时，不可相加当成总运行时间。记录实际响应模型名、开始结束时间、数据哈希和逐次原始响应。没有虚构 token 单价或费用；实际 usage 留在原始响应。

## 结果怎么解释

先看运行是否成功，再比较质量。若失败很多，先解释接口可靠性；若覆盖率不同，不能只比较有效回答准确率。检查分类混淆集中在哪两类，布尔任务是否把否定或政策询问误当退款，量表任务是否正确执行明确规则。

概率是模型估计，不等于校准证据。置信度公式只是对概率分布的数学变换。小样本 Brier 可作描述性指标，不能证明概率在真实业务上准确。没有进行统计显著性检验；如果要可靠比较，应扩大独立测试集，预注册模板，固定模型版本，多次运行并用配对方法估计不确定性。

## 验证范围

离线测试覆盖 HTTP、请求验证、认证、三题型、结构化输出适配、缺 Key、拒答、截断、错误概率、重试、超时、指标计算、数据构建和失败记录，共 20 项；离线完整演示验证了 36 次 HTTP 请求和报告落盘。

真实模型调用与线上 Jev 契约已于 2026-10-12 验证：36 条样本、48 个答案在本地服务与 Jev 上各跑一遍，合计 72 次请求、0 失败、覆盖率均 100%，返回模型分别为 `deepseek-flash` 与 `typesafe/jev-1.13-20260917`。完整记录见 `docs/VERIFICATION.md`，结果分析见 `docs/REPORT.md`。

评测器对返回值有一道接受门槛（`validateResponse`）：类型必须匹配、概率分布键集合必须一致且和为 1、choice 必须是最大概率项、score 必须在量程内且 legend 键匹配。厂商对 `probabilities` 只保留两位小数而 `score` 保留全精度，因此 score 的自洽性容差按等级数放宽（3 级为 0.05）；此前 0.01 的容差会把 12 条 Jev score 答案中的 3 条误判为无效。**这道门槛只影响评测器接受哪些响应，不改变任何发送给服务的内容**，因此不影响两个服务的公平比较。

不要把"离线测试通过"或"本地演示成功"解释成外部依赖已经验证；反之，外部依赖已验证也不代表代码在别的网络环境、模型版本下同样成立。
